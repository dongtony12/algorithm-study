# 11. Container With Most Water

- **난이도**: **Medium** ← Easy 라운드 중 사용자 지정으로 조기 투입 (2026-08-16)
- **유형**: 배열, **투 포인터(양끝 → 안쪽)**, 지배 논증
- **링크**: https://leetcode.com/problems/container-with-most-water/
- **최초 풀이**: 2026-08-16 / **결과**: 통과 (구현 1발). **접근 단계를 건너뛰고 코드부터 제출** → "왜 되는가"를 사후에 보강

---

## 문제 요약

`height[i]` 는 `(i, 0)` ~ `(i, height[i])` 수직 선분. **두 선분 + x축으로 만든 통에 담기는 물의 최대량**을 반환.

```
넓이 = min(height[i], height[j]) × (j - i)
        └─ 높이는 낮은 쪽이 결정 ─┘   └ 폭 ┘
```

**왜 `min` 인가**: 통은 낮은 쪽 벽 높이까지만 물을 담는다. 높은 쪽으로 넘쳐흐른다.

```
[1,8,6,2,5,4,8,3,7]  →  49    (index 1의 8, index 8의 7 → min(8,7) × 7 = 49)
[1,1]                →  1
```

- **Constraints**: `2 <= n <= 10^5`, `0 <= height[i] <= 10^4`
  ← **`n = 10⁵` 이므로 브루트포스 `O(n²)` = 10¹⁰ 은 죽는다.** `O(n)` 이 필요

---

## 최종 정답

```ts
function maxArea(height: number[]): number {
    let i = 0
    let k = height.length - 1

    let maxArea = 0

    //x가 최대고 height가 클때인데 height는 2개의 value중 작은값
    while (k > i){
        let x = k - i
        let y = 0

        if(height[i] > height[k]){
            y = height[k]
            k--
        }else {
            y = height[i]
            i++
        }

        let area = x * y

        if(maxArea <= area) {
            maxArea = area
        }
    }

    return maxArea
}
```

- **시간 `O(n)` / 공간 `O(1)`**
- 검증: 고정 13건 + 랜덤 **30만건**(브루트포스 대조) 불일치 0. 최대 입력(10⁵) 200회 28ms

**구현에서 잘한 것**
- **폭 `x = k - i` 를 포인터 이동 *전에* 계산** — 옮기고 나서 재면 틀린 넓이가 나온다
- `y` 를 분기 안에서 자연스럽게 `min` 으로 잡음 (별도 `Math.min` 호출 없이)

## 🔑 왜 되는가 — 지배 논증

이 문제의 진짜 난이도는 여기다. **"낮은 쪽을 버려도 안전한 이유".**

### 구체적으로

```
height = [1, 8, 6, 2, 5, 4, 8, 3, 7]
          ↑                       ↑
       i=0 (높이 1)            k=8 (높이 7)

현재 넓이 = min(1, 7) × (8-0) = 1 × 8 = 8
```

**높이 1을 버리지 않고 `k`만 계속 당기면:**

| 조합 | 높이 | 폭 | 넓이 |
|---|---|---|---|
| (0, 8) | `min(1,7)` = 1 | 8 | **8** ← 지금 |
| (0, 7) | `min(1,3)` = 1 | 7 | 7 |
| (0, 6) | `min(1,8)` = 1 | 6 | 6 |
| (0, 5) | `min(1,4)` = 1 | 5 | 5 |
| … | **전부 1** | 점점 ↓ | 점점 ↓ |

**높이는 `1`에 갇혀 절대 안 커지고, 폭은 반드시 줄어든다.**

### 일반화

```
height[i] 를 포함하는 남은 조합은 전부 (i, j),  j < k       ← 폭이 반드시 줄어든다
높이 = min(height[i], height[j]) ≤ height[i]                 ← 높이는 절대 못 넘는다

→ 두 항 모두 커질 수 없다
→ height[i] 를 포함하는 어떤 미래 조합도 현재 넓이를 넘지 못한다
→ 현재 넓이는 이미 maxArea 에 기록했으므로 버려도 안전 ✅
```

### 왜 "높은 쪽"을 옮기면 안 되나

높은 쪽(`k`)을 옮기면 `height[i]` 가 그대로 남아 있으므로:

```
높이 = min(height[i], height[새 k])  →  여전히 height[i] 이하   (안 커짐)
폭                                   →  반드시 줄어든다        (작아짐)
```

**두 항 모두 안 커진다.** 아무것도 얻지 못하고 기회만 날린다.
반면 **낮은 쪽을 옮기면 높이 제한이 풀린다** — 넓이가 커질 수 있는 **유일한 경로**다.

> ### 🔑 [0167. Two Sum II - Input Array Is Sorted](../0167-two-sum-ii-input-array-is-sorted/README.md) 와 같은 지배 논증, 다른 근거
> | | 버려도 되는 근거 |
> |---|---|
> | 167 | **정렬** — 남은 것 중 최소/최대가 보장됨 |
> | **11** | **낮은 쪽이 min을 결정 + 폭은 단조 감소** — 정렬이 없어도 성립 |
>
> 공통 형태: **"지금 최선의 조합조차 안 되면, 나머지는 볼 필요도 없다."** → [투 포인터](../../concepts/two-pointers.md) · [그리디 알고리즘](../../concepts/greedy.md)

## ⚠️ 접근 단계에서 나온 잘못된 논거

> *"혹시나 최대 area를 계산하게 되더라도 n번 반복하게 되고 **max만 값을 저장하므로 상관없음**"*

**❌ 위험한 오해다.** 버린 후보가 정답이었다면 **`max`에도 안 들어간다.**
`max` 저장은 "본 것 중 최대"를 기억하는 것일 뿐, **안 본 것을 구제해주지 않는다.**

필요한 건 정확히 **"버리는 그 후보는 절대 정답일 수 없다"** 는 증명이다.

> *"폭이 줄더라도 **높이가 더 커지는쪽을 기대하고** 옮겨감"*

**기대는 근거가 아니다.** 실제로는 "커질 수도 있다"가 아니라 **"낮은 쪽을 안 버리면 절대 못 커진다"** 가 논증이다.

## 알아야 할 상식

### 1. 브루트포스가 왜 죽는가

```
n = 10⁵  →  n(n-1)/2 ≈ 5 × 10⁹ 쌍
```
Constraints를 먼저 봤다면 `O(n²)` 는 즉시 후보에서 탈락한다. → [0121. Best Time to Buy and Sell Stock](../../01-Array-String/0121-best-time-to-buy-and-sell-stock/README.md) 의 같은 교훈

### 2. 같은 값일 때 어느 쪽을 옮기나

```ts
if (height[i] > height[k]) { ... k-- } else { ... i++ }   // 같으면 i++
```
**둘 다 정답이다.** 높이가 같으면 어느 쪽을 옮겨도 남은 조합의 상한이 동일하게 제한되기 때문.
(면접에서 "같을 땐 어느 쪽이죠?" 를 물으면 → "어느 쪽이든 됩니다, 이유는 …" 이라고 답하면 좋다)

### 3. `maxArea <= area` vs `maxArea < area`

```ts
if (maxArea <= area) maxArea = area
```
같을 때도 대입하므로 **불필요한 쓰기**가 발생한다. `<` 로 충분.
동작은 같지만 의도가 더 명확해진다.

### 4. 변수명 `maxArea` 가 함수명과 같다

```ts
function maxArea(height: number[]): number {
    let maxArea = 0        // 함수와 같은 이름 — 안쪽 스코프가 바깥을 가린다(shadowing)
```
동작에는 문제없지만(재귀를 안 쓰므로), **재귀로 바꾸는 순간 자기 자신을 못 부른다.** `best`, `result` 등으로.

## 실수 노트

- **접근 단계를 건너뛰고 코드부터 제출** → 이 문제는 구현보다 **"왜 버려도 되는가"** 가 훨씬 어려운데 그걸 사후에 보강해야 했다. 코드가 맞았어도 논증이 없으면 **조건이 살짝 바뀌면 바로 틀린다**
- **`max만 저장하므로 상관없다`** 를 근거로 삼음 → 버린 후보가 정답이면 max에도 안 들어간다. **"버린 것이 정답일 수 없음"을 증명해야 한다**
- **`기대하고 옮겨감`** → 기대는 근거가 아니다. "안 버리면 절대 못 커진다"가 논증
- `maxArea <= area` — 같을 때 불필요한 대입 `#죽은코드방치` (카운트 미포함, 정답 코드의 스타일)
- 변수명 `maxArea` 가 함수명과 충돌(shadowing) `#변수명불명확` (카운트 미포함)
- ✅ **폭을 포인터 이동 전에 계산** — 순서를 정확히 잡음
- ✅ 복잡도 `O(n)` / `O(1)` 정확 (7문제 연속 공간복잡도 정확)
- ✅ 구현 1발 통과 (수정 0회)

### 2026-08-28 (1회차) — 통과, 논증에 힌트 2회 · `1일` → `3일` 단계

```
고정 10/10  ·  완전탐색 대조 20만건 불일치 0건
구조적 케이스 5만건 불일치 0건 (단조증가 / 단조감소 / 전부동일 / 산 모양)
10만 입력 × 2000회: 223ms
참고 — O(n²) 는 2만개만으로도 409ms  →  10만이면 약 10초 (TLE)
```

```ts
function maxArea(height: number[]): number {
    let left = 0
    let right = height.length - 1
    let area = 0

    while (left < right) {
        let width = right - left
        let curArea = width * Math.min(height[left], height[right])
        if (curArea > area) area = curArea

        if (height[left] < height[right]) left++
        else right--
    }
    return area
}
```

**코드는 백지에서 첫 시도에 정확.** 복잡도 `O(n)` / `O(1)` 도 정확.

#### ⚠️ 논증을 먼저 제시하지 않음 — 힌트 2회 후 완성

`if (height[left] < height[right]) left++` 이 한 줄이 **후보를 통째로 버린다.**

`height = [1,8,6,2,5,4,8,3,7]` 의 첫 스텝:

```
left=0 (높이 1),  right=8 (높이 7)   →  height[0] < height[8] 이므로 left++

이 순간 버려지는 조합:
  (0,7), (0,6), (0,5), (0,4), (0,3), (0,2), (0,1)   ← 0번 선이 낀 나머지 전부
```

**7개를 한 번도 계산하지 않고 버렸는데 답이 맞았다.** 왜?

**1차 답 (높이 축만)**: *"항상 가장 작은 height를 기준으로 area를 계산하기 때문에 제일 작은 height 값은 버리고 진행해도 괜찮음"*
→ 절반만 맞다. **높이만으로는 결론이 안 난다.** 반론이 가능하다 — *"높이가 낮아도 너비가 훨씬 넓으면 넓이는 더 클 수 있지 않나?"*

**2차 답 (너비 축)**: *"안쪽으로 줄어들수록 너비는 무조건 줄어들기 때문에 현재 계산값보다 더 작아짐"*
→ ✅ 포인터가 **양 끝에서 시작해 안쪽으로만** 움직이므로, **지금 이 순간의 너비가 그 선을 낀 조합 중 최대**다.

---

### 지배 논증 — 두 축을 합치면

`0`번을 낀 임의의 조합 `(0, j)` (단 `j < 8`) 와 방금 계산한 `(0, 8)` 을 비교:

| | `(0, j)` | `(0, 8)` | |
|---|---|---|---|
| **너비** | `j` | `8` | `j < 8` → **더 작다** |
| **높이** | `min(h[0], h[j]) ≤ h[0]` | `min(h[0], h[8]) = h[0]` | **더 작거나 같다** |
| **넓이** | | | **반드시 더 작거나 같다** |

> ### 🔑 두 축 모두 열세이므로 곱도 열세 → **지배(dominated)**
> `(0, 8)` 을 이미 계산했으므로 나머지 7개는 **계산할 가치가 없다.** 버려도 최댓값을 놓칠 수 없다.

그리고 이 논증이 **매 스텝 똑같이 성립**한다. 좁혀질 때마다 *"현재 너비가 그 선을 낀 남은 조합 중 최대"* 라는 조건이 유지되므로.
→ `O(n)` 에 전수 탐색과 같은 답이 나온다.

### 왜 **짧은 쪽**을 버려야 하나

`height[left] < height[right]` 인데 `right--` 를 하면:

- 높이는 여전히 `height[left]` 가 병목 → **안 늘어남**
- 너비는 줄어듦 → **손해**

**짧은 쪽을 버려야만** 높이가 개선될 **가능성**이 생긴다. 유일하게 이득을 볼 수 있는 방향.
