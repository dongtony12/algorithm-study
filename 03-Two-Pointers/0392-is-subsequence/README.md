# 392. Is Subsequence

- **난이도**: Easy
- **유형**: 문자열, **투 포인터(같은 방향, 속도 다름)**
- **링크**: https://leetcode.com/problems/is-subsequence/
- **최초 풀이**: 2026-08-10 / **결과**: 통과 (**3차 수정** — 빈 문자열 엣지케이스. 힌트 없이 반례 지적만으로 스스로 수정)
- **챕터**: Two Pointers 완료 문제

---

## 문제 요약

`s`가 `t`의 **subsequence**인지 판정.
subsequence = 원본에서 **일부를 지우되(0개도 가능) 남은 순서는 유지**해 만들 수 있는 문자열.

```
s = "abc", t = "ahbgdc"  →  true
s = "axc", t = "ahbgdc"  →  false   ('c'가 'x' 뒤에 없음)
s = "aec", t = "abcde"   →  false   (순서 뒤집힘)
```

- **Constraints**: **`0 <= s.length <= 100`**, **`0 <= t.length <= 10^4`** ← **둘 다 0 가능. 이게 이번 함정이었다.**
- 소문자 영문자만

---

## 접근 — 루프의 주인은 `t`가 아니라 `s`

두 포인터가 **같은 방향**으로 가되 **속도가 다르다.**

```
s = "a b c"          k (느림 — 매칭될 때만 전진)
     0 1 2

t = "a h b g d c"    i (빠름 — 매 반복 무조건 전진)
     0 1 2 3 4 5
```

| 단계 | k | i | s[k] vs t[i] | 동작 |
|---|---|---|---|---|
| 1 | 0 `a` | 0 `a` | ✅ | `i++`, `k++` |
| 2 | 1 `b` | 1 `h` | ❌ | `i++` 만 |
| 3 | 1 `b` | 2 `b` | ✅ | `i++`, `k++` |
| 4 | 2 `c` | 3 `g` | ❌ | `i++` 만 |
| 5 | 2 `c` | 4 `d` | ❌ | `i++` 만 |
| 6 | 2 `c` | 5 `c` | ✅ | `i++`, `k++` → `k = 3 = s.length` |

`k`가 `s.length`에 도달 = **s를 다 소진** = `true`.
**되돌아가지 않는다** — 한 번 지나친 `t[i]`는 다시 볼 필요가 없다. 그리디하게 **가장 왼쪽에서 매칭되는 것을 잡으면** 뒤에 남는 선택지가 최대가 되기 때문. → [그리디 알고리즘](../../concepts/greedy.md)

### ⚠️ 관점 전환 — 이 문제의 진짜 핵심

| | 루프 조건 | 결과 |
|---|---|---|
| ❌ 1~3차 시도 | `while (i < t.length)` — **"t를 다 훑는다"** | `t = ""` 면 루프가 **0번** 돌아 성공 판정 기회조차 없음 |
| ✅ 최종 | `while (k < s.length)` — **"s를 다 소진한다"** | `s = ""` 면 루프가 0번 돌고 바로 `true` — 가드 불필요 |

> **성공 조건이 곧 루프 조건이어야 한다.**
> 이 문제의 성공은 "t를 다 봤다"가 아니라 **"s를 다 소진했다"** 이다.
> 루프 조건을 성공 조건으로 잡으면 **탈출 = 성공**이 되어 엣지케이스가 저절로 풀린다.

## 최종 정답

```ts
function isSubsequence(s: string, t: string): boolean {
    let k = 0   // s의 포인터
    let i = 0   // t의 포인터

    while (k < s.length) {
        if (i === t.length) {
            return false          // t를 다 썼는데 s가 남음
        }

        if (s[k] === t[i]) {
            i++
            k++
        } else {
            i++
        }
    }

    return true                   // s를 다 소진 = 성공
}
```

- **시간 `O(n)` / 공간 `O(1)`** (`n` = `t.length`)

### 엣지케이스 검증 (node 17/17 통과)

| 입력 | 동작 | 결과 |
|---|---|---|
| `("", "")` | `while(0 < 0)` 즉시 거짓 | `true` ✅ ← **처음 3번 틀렸던 케이스** |
| `("", "ahbgdc")` | 동일 | `true` ✅ |
| `("abc", "")` | 첫 반복에서 `i === t.length` | `false` ✅ |
| `("aa", "aba")` | 중복 문자, 떨어져 매칭 | `true` ✅ |
| `("aaa", "aa")` | 개수 부족 | `false` ✅ |

최대 입력(`t` = 10⁴, 1000회 반복) 0.6ms / 최악 케이스 30.6ms — TLE 여유.

## ⚠️ 복잡도 — `n`이 어느 쪽인지 정의해야 한다

**틀리게 답한 부분**: `O(n)` 이라고만 씀. **`n`이 `s`인지 `t`인지 정의가 없었다.**

| 기호 | 뜻 | 상한 |
|---|---|---|
| `m` | `s.length` | 100 |
| `n` | `t.length` | 10⁴ |

### 시간복잡도 `O(n)`

```
while (k < s.length) {          ← 조건에 쓰인 변수는 k
    if (i === t.length) return false
    if (일치) { i++; k++ }
    else      { i++ }           ← i는 어느 쪽이든 반드시 +1
}
```

- `i`는 **매 반복 무조건 1 증가** → 반복 횟수 상한은 `n + 1`
- `k`는 매칭될 때만 증가 → 상한을 정하지 못함
- **최악**: `t`를 끝까지 훑고 실패 (`s = "z"`, `t = "aaa...a"`) → `O(n)`
- **최선**: `s`가 `t`의 접두사 → `O(m)`

> ### 🔑 `while` 조건에 쓰인 변수 ≠ 반복 횟수를 결정하는 변수
> **"매 반복마다 반드시 증가하는 변수가 무엇인가"** 를 찾으면 그게 상한이다.
> 조건문 생김새(`k < s.length`)만 보고 `O(m)`이라 답하면 틀린다.

### `m`은 왜 식에 안 나오나

`m`은 **상한이 아니라 조기 종료**에만 관여한다. Big-O는 최악 기준이므로 `O(n)`.
`m > n` 이면 즉시 `false`로 끝나므로 `O(m)`이 되는 일도 없다.

### 공간복잡도 `O(1)`

변수 `k`, `i` 두 개뿐. **배열/Map 생성 없음.** → 정확히 답함.

### [0014. Longest Common Prefix](../../01-Array-String/0014-longest-common-prefix/README.md) 와 비교

거기선 `m × k` 두 축을 `n` 하나로 뭉개서 `O(n²)`이라 틀렸다.
여기서도 **축을 정의 안 하는 습관**이 그대로 나왔다. 다만 이번엔 **한 축만 남는 게 정답**이라는 점이 다르다.

> **축이 둘이면 → 둘 다 쓴다 (`O(m × k)`)**
> **축이 둘인데 하나만 상한이면 → 어느 쪽인지 명시한다 (`O(n)`, `n = t.length`)**
> 어느 쪽이든 **"n이 뭔지 먼저 정의"** 가 출발점.

## Follow-up — 쿼리가 10억 개라면

> `t`는 **고정**인데 `s1 … sk` (k ≥ 10⁹) 가 들어온다면?

지금 코드로는 `O(k × n)` = 10⁹ × 10⁴ = **10¹³** → 불가능.
낭비의 정체: `t`가 한 글자도 안 변하는데 **매 쿼리마다 `t`를 처음부터 훑는다.**

### 전처리 — 문자별 등장 위치 인덱싱

```
t = "abcabc"
     012345

'a' → [0, 3]      ← 오름차순 보장 (왼쪽부터 넣었으므로)
'b' → [1, 4]
'c' → [2, 5]
```

병목이던 질문 **"위치 `i` 이후에서 문자 `c`가 처음 나오는 인덱스는?"** 이
**"정렬된 배열에서 `i`보다 큰 첫 값"** 으로 바뀐다 → **이진 탐색** `O(log n)`.

```ts
class SubsequenceChecker {
  private pos = new Map<string, number[]>();

  constructor(t: string) {                    // 전처리 — 딱 한 번
    for (let i = 0; i < t.length; i++) {
      if (!this.pos.has(t[i])) this.pos.set(t[i], []);
      this.pos.get(t[i])!.push(i);
    }
  }

  check(s: string): boolean {
    let prev = -1;                            // 직전에 매칭된 t의 인덱스
    for (const ch of s) {
      const list = this.pos.get(ch);
      if (!list) return false;                // t에 아예 없는 문자
      const idx = upperBound(list, prev);
      if (idx === list.length) return false;  // prev 이후로 남은 게 없음
      prev = list[idx];
    }
    return true;
  }
}

function upperBound(arr: number[], target: number): number {
  let lo = 0, hi = arr.length;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (arr[mid] > target) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}
```

| | 전처리 | 쿼리 1회 | 전체 (k = 10⁹) |
|---|---|---|---|
| 지금 해답 | 없음 | `O(n)` | `O(k × n)` ❌ |
| 이진 탐색 | `O(n)` 시간·공간 | `O(m log n)` | `O(n + k·m·log n)` ✅ |
| `next[i][c]` DP | `O(26n)` | `O(m)` | 더 빠르지만 공간 26배 |

> ### 🔑 "고정된 입력 + 반복 쿼리" = 전처리 신호
> 쿼리마다 **똑같은 스캔**을 반복하고 있으면 그 결과를 미리 인덱싱할 수 있는지 본다.
> 실무의 **DB 인덱스**와 정확히 같은 발상 — 읽기가 압도적으로 많으면 쓰기 시점에 비용을 옮긴다.

→ [투 포인터](../../concepts/two-pointers.md) · 이진 탐색은 `11-Binary-Search` 챕터에서 다시

## 알아야 할 상식

### 1. `else { i++ }` 는 생략 가능

```ts
while (k < s.length) {
    if (i === t.length) return false
    if (s[k] === t[i]) k++      // 일치할 때만 k 전진
    i++                          // i는 어차피 항상 전진
}
return true
```
`if`/`else` 양쪽에 `i++`가 똑같이 있으면 **밖으로 빼낸다.** 코드가 짧아지고 "i는 무조건 전진"이라는 불변식이 눈에 보인다.

### 2. `for` 루프로 쓰면 더 짧다

```ts
function isSubsequence(s: string, t: string): boolean {
  let k = 0;
  for (const ch of t) {
    if (k < s.length && s[k] === ch) k++;
  }
  return k === s.length;
}
```
`t`를 전부 훑으므로 **조기 종료는 못 하지만**(항상 `O(n)`) 가장 읽기 쉽다. 면접에서 먼저 이걸 쓰고 "조기 종료를 넣으면 이렇게 됩니다"로 확장하는 것도 좋은 전개.

### 3. 가드는 루프 **밖**에 둔다

```ts
while (i < t.length) {
    if (t.length === 0) return false   // ❌ 도달 불가능 — 루프가 0번 돌면 실행 안 됨
```
**루프 조건이 거짓이면 몸통은 한 번도 실행되지 않는다.** 루프가 0번 도는 입력을 처리하려면 가드는 반드시 **루프 진입 전**에 있어야 한다.
→ 더 좋은 건, 애초에 **가드가 필요 없도록 루프 조건을 성공 조건으로 잡는 것.**

### 4. 실무 연결 — 도달 불가능 코드

```ts
// 배열이 비어 있으면 콜백이 한 번도 안 불린다
items.forEach(item => {
  if (items.length === 0) return setEmpty(true);   // ❌ 절대 실행 안 됨
});
```
`map`/`forEach`/`filter` 안에 "빈 배열 처리"를 넣는 실수와 같은 구조. **0회 실행 케이스는 루프 밖에서 처리한다.**

## 실수 노트

- **빈 문자열 엣지케이스를 3번 연속 놓쳤다** → Constraints의 `0 <= s.length`, `0 <= t.length` 를 안 봤다. **문제 읽는 순서: 제목 → Constraints → 본문** `#Constraints미확인` `#엣지케이스누락`
- **가드를 `while` 몸통 안에 넣었다** → 루프가 0번 도는 입력에선 도달조차 못 한다 `#루프0회케이스`
- **`t.length === 0 → false`** 로 반환값까지 틀렸다 → `s`도 비었으면 `true`. **가드를 넣기 전에 "이 조건일 때 정답이 뭐지"를 먼저 확정할 것** `#엣지케이스누락`
- **`O(n)`의 `n`을 정의하지 않았다** → [0014. Longest Common Prefix](../../01-Array-String/0014-longest-common-prefix/README.md) 와 동일. 축이 둘이면 반드시 기호부터 정의 `#복잡도차원뭉개기`
- ✅ **공간복잡도 `O(1)` 정확** (3문제 연속)
- ✅ **힌트 없이 반례 지적만으로 스스로 구조를 재설계함** — 루프의 주인을 `t`→`s`로 바꾼 건 이 문제의 핵심을 정확히 짚은 것

복잡도 `O(n)`(`n` = t.length) / `O(1)` 정확.

```ts
function isSubsequence(s: string, t: string): boolean {
    let i = 0
    let j = 0

    while (i < s.length) {
        if (j === t.length) {
            return false
        }
        if (s[i] === t[j]) {
            i++
        }
        j++
    }
    return true
}
```

```
s = "aec",  t = "abcde"

개수로만 보면 a·e·c 전부 t에 있다  →  true 반환
그런데 정답은 false

t = a  b  c  d  e
    0  1  2  3  4
  'a' → 0 ✅   'e' → 4 ✅   'c' → 4 이후에 있어야 하는데 c는 2  ❌
```

> ### 🔑 개수를 세는 순간 **"순서" 정보가 통째로 사라진다**
> [0242. Valid Anagram](../../02-Hashmap/0242-valid-anagram/README.md) 은 *"순서와 위치가 답에 영향을 주지 않는다"* 가 논증의 핵심이었다. 이 문제는 **정반대** — subsequence의 정의가 *"상대 순서 유지"* 다.
>
> **패턴을 가져오기 전에 항상 확인: "이 문제에서 순서가 답에 영향을 주는가?"**
> - 영향 없음 → 개수 세기 (`242`, `383`)
> - **영향 있음 → 순서를 지키며 훑기** (`392`)

✅ 지적 후 스스로 일반화함 — *"26칸 배열은 소문자이면서 **순서가 영향을 안 줄 때만** 쓰는 거구나"*

#### 🔑 왜 그리디하게 가장 왼쪽에서 매칭해도 되는가

```
t = "a a b c"        s = "ab"
     0 1 2 3

t[0]의 'a'로 잡으면  →  남은 구간 t[1..3] = "abc"
t[1]의 'a'로 잡으면  →  남은 구간 t[2..3] = "bc"
                                    └─ 포함관계 ─┘
```

**앞에서 잡을수록 뒤에 남는 구간이 크고, 큰 구간은 작은 구간을 포함한다.**
→ **오른쪽에서 잡아 성공하는 경우가 있다면 왼쪽에서 잡아도 반드시 성공한다** → 왼쪽 매칭은 절대 손해가 아니다.

[0167. Two Sum II - Input Array Is Sorted](../0167-two-sum-ii-input-array-is-sorted/README.md)(정렬) · [0011. Container With Most Water](../0011-container-with-most-water/README.md)(min 결정 + 폭 단조감소)와 같은 형태의 **교환 논증**. → [그리디 알고리즘](../../concepts/greedy.md)

#### 복잡도 — 상한을 정하는 건 `t` 포인터

1차 답변은 `O(m+n)`. 기호를 정의하고 나니 **한 축이 떨어졌다.**

```
m = s.length (≤ 100),  n = t.length (≤ 10⁴)

s의 포인터(i)는 매칭될 때만 전진  →  상한을 못 정한다
t의 포인터(j)는 매 반복 전진      →  반복 횟수는 n 으로 묶인다

→ O(n)
```

> 이 문제 노트에 **본인이 적어둔 교훈** 그대로: *"`while` 조건에 쓰인 변수 ≠ 반복 횟수를 결정하는 변수"*
