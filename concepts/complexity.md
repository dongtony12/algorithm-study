# 시간·공간 복잡도

> 모든 알고리즘 문제의 채점 기준. 정답을 맞히는 것 다음으로 중요하다.

---

## 1. 왜 "초"로 재지 않는가

같은 코드도 컴퓨터 사양·언어·그날 CPU 상태에 따라 실행 시간이 달라진다.
그래서 **절대 시간이 아니라 "입력이 커질 때 얼마나 가파르게 느려지는가"**, 즉 **증가율**을 잰다.

```
입력 n이 2배가 되면 연산량은 몇 배가 되는가?
```

- `O(n)` → 2배
- `O(n²)` → 4배
- `O(log n)` → +1번

---

## 2. Big-O 표기 규칙

### 규칙 1. 상수는 버린다
`3n` → `O(n)`, `100` → `O(1)`
n이 충분히 커지면 상수 배는 증가 "모양"을 바꾸지 못한다.

### 규칙 2. 최고차항만 남긴다
`n² + 1000n + 5` → `O(n²)`
n = 1,000,000이면 `n²`가 나머지를 압도한다.

### 규칙 3. 최악의 경우를 센다
운 좋게 첫 줄에서 찾는 경우가 아니라, **끝까지 못 찾는 경우**를 기준으로 한다.

---

## 3. 시간복잡도 — 코드에서 읽어내는 법

| 코드 모양 | 복잡도 |
|---|---|
| 단일 연산, 조건문 | `O(1)` |
| `for` 1중 | `O(n)` |
| `for` 2중 (중첩) | `O(n²)` |
| `for` 나란히 2개 (중첩 아님) | `O(n)` ← 더하기라 `2n` → `n` |
| 매번 절반씩 줄임 (이진 탐색) | `O(log n)` |
| 정렬 | `O(n log n)` |
| 모든 부분집합 | `O(2ⁿ)` |
| 모든 순열 | `O(n!)` |

```js
// O(n) — 나란히 있으면 더하기
for (const x of arr) { ... }   // n
for (const x of arr) { ... }   // n   →  2n → O(n)

// O(n²) — 중첩이면 곱하기
for (const x of arr) {         // n
  for (const y of arr) { ... } //   × n  →  O(n²)
}
```

⚠️ **숨어 있는 반복문에 주의.** 메서드 안에도 반복문이 있다.
```js
for (const x of arr) {        // n
  if (other.includes(x)) ...  //   × m   ← includes는 O(m)!
}
// → O(n·m), 겉보기엔 1중 for
```

## 4. 공간복잡도 — 핵심 개념

### 세는 것은 "추가로(auxiliary) 쓴 공간"뿐

> **입력을 담는 공간은 세지 않는다.**

왜? 입력은 **어떤 알고리즘을 쓰든 어차피 존재해야 하는 공간**이라, 알고리즘끼리 비교하는 데 아무 의미가 없기 때문이다. 공정한 비교를 위해 제외한다.

### 이사 비유

방(입력 배열)에 짐이 n개 있고, 이걸 정리해야 한다.

| | 방법 | 임시 창고 | 공간복잡도 |
|---|---|---|---|
| A | 짐을 전부 창고에 뺐다가 순서대로 다시 넣는다 | n칸 | `O(n)` |
| B | 방 안에서 물건 자리만 서로 바꾼다 | 0칸 | `O(1)` |

**방 자체(= 입력)는 둘 다 똑같이 필요하므로 계산에서 뺀다.** 세는 건 오직 **창고**다.

### 등급

| 코드 | 공간복잡도 |
|---|---|
| 변수 몇 개 (`let i, j, k`) | `O(1)` — 개수가 n과 무관 |
| 새 배열/Map/Set 생성 (크기 n) | `O(n)` |
| 2차원 DP 테이블 `n×n` | `O(n²)` |
| 깊이 n짜리 재귀 | `O(n)` ← **콜스택** |

## 5. 88번에 적용해보기

### 최적 풀이가 왜 `O(1)`인가

```js
function merge(nums1, m, nums2, n) {
  let i = m - 1;       // ← 변수 1
  let j = n - 1;       // ← 변수 2
  let k = m + n - 1;   // ← 변수 3

  while (j >= 0) {
    if (i >= 0 && nums1[i] > nums2[j]) nums1[k--] = nums1[i--];
    else                               nums1[k--] = nums2[j--];
  }
}
```

- `nums1`, `nums2` → **입력이다. 안 센다.**
- `nums1[k] = ...` → **이미 존재하는 칸에 덮어쓰는 것.** 새 공간을 만든 게 아니다.
- 새로 만든 것 = `i`, `j`, `k` **숫자 변수 3개뿐**

m, n이 10이든 1,000,000이든 **변수는 항상 3개**다.
→ 추가 공간이 입력 크기와 **무관한 상수** → **`O(1)`**

> `O(1)` = "공간을 안 쓴다"가 아니라 **"n이 커져도 추가 공간이 늘지 않는다"**

### 내 첫 풀이는 왜 `O(1)`이 아닌가

```js
nums1.push(...nums2)
nums1.sort((a, b) => a - b)   // ← 여기
```

`nums1` 자체는 입력이라 안 세지만, **`sort()`가 내부적으로 보조 배열을 만든다.**
V8의 `Array.prototype.sort`는 TimSort라서 최악의 경우 원소 수에 비례하는 임시 버퍼를 쓴다.
→ **`O(m+n)`**

참고 — 언어별 정렬의 추가 공간:

| 언어 | 알고리즘 | 추가 공간 |
|---|---|---|
| JS (V8) | TimSort | `O(n)` |
| Java (객체) | TimSort | `O(n)` |
| Java (원시타입) | Dual-Pivot Quicksort | `O(log n)` |
| C++ | Introsort | `O(log n)` |

## 6. 재귀의 공간복잡도 — 콜스택

**나중에 트리 문제에서 반드시 걸리는 부분.**

```js
function depth(node) {
  if (!node) return 0;
  return 1 + Math.max(depth(node.left), depth(node.right));
}
```

새 배열을 하나도 안 만들었는데 공간복잡도는 `O(1)`이 아니다.
함수가 자기를 부를 때마다 **콜스택에 프레임이 쌓이기 때문**이다.

- 균형 잡힌 트리 → 깊이 `O(log n)` → 공간 `O(log n)`
- 한쪽으로 치우친 트리(사실상 연결 리스트) → 깊이 `O(n)` → 공간 `O(n)`

> **재귀의 공간복잡도 = 최대 재귀 깊이**

## 7. 암산법 — Constraints 보고 3초 만에 판단하기

### 외울 것은 하나

> # 1초 ≈ 1억 번 (`10⁸`)

C++ 기준. **JS는 2~5배 느리므로 `10⁷`을 안전선**으로 잡는다.

### 계산법: 복잡도 식에 n을 대입

`n = 10⁵` 일 때:

| 복잡도 | 연산 횟수 | 시간 | 판정 |
|---|---|---|---|
| `O(n)` | `10⁵` = 10만 | 0.001초 | ✅ |
| `O(n log n)` | `10⁵ × 17` = 170만 | 0.02초 | ✅ |
| `O(n²)` | `(10⁵)²` = `10¹⁰` = **100억** | **100초** | ❌ |

### 지수 계산 — 지수끼리 더한다

```
10ᵃ × 10ᵇ = 10⁽ᵃ⁺ᵇ⁾
(10⁵)² = 10⁵ × 10⁵ = 10¹⁰
```

| 지수 | 값 | 한글 |
|---|---|---|
| `10⁴` | 10,000 | 만 |
| `10⁶` | 1,000,000 | 백만 |
| **`10⁸`** | 100,000,000 | **1억 ← 기준선(1초)** |
| `10¹⁰` | 10,000,000,000 | 100억 (=100초) |

### `log₂` 어림값

| n | `log₂(n)` |
|---|---|
| `10³` (천) | ≈ **10** |
| `10⁵` (십만) | ≈ **17** |
| `10⁶` (백만) | ≈ **20** |
| `10⁹` (십억) | ≈ **30** |

**`log`는 아주 작다.** `n`이 10억이어도 30. 그래서 `O(n log n)`은 `O(n)`의 20~30배 수준이고 **거의 항상 통과한다.**

### 역산표 — 이걸 외우면 계산이 필요 없다

| 복잡도 | 감당 가능한 최대 n | 기억법 |
|---|---|---|
| `O(n!)` | **~10** | 10! = 360만 |
| `O(2ⁿ)` | **~20~25** | 2²⁵ = 3300만 |
| `O(n³)` | **~500** | 500³ = 1.25억 |
| **`O(n²)`** | **~10⁴ (만)** | **(10⁴)² = 10⁸ = 1억** ← 가장 중요 |
| `O(n log n)` | **~10⁶ (백만)** | 10⁶ × 20 = 2000만 |
| `O(n)` | **~10⁷ (천만)** | |

> **`O(n²)`의 한계선 = `n = 10⁴`.** 이것만 외워도 절반은 해결.

### 실전 루틴 (3초)

```
1. Constraints에서 n의 상한 확인       → 10⁵
2. 역산표에서 위치 찾기                → 10⁴ < 10⁵ ≤ 10⁶
3. 목표 복잡도 확정                    → O(n log n) 또는 O(n)
4. "이중 반복문은 후보에서 제외"        → 접근법을 처음부터 다르게
```

**코드를 한 줄도 쓰기 전에 방향이 정해진다.**
→ 문제 읽는 순서: **제목 → Constraints → 본문**

## 8. 입력 크기로 목표 복잡도 역산하기

문제의 제약조건(`Constraints`)에 적힌 n을 보면 **어떤 복잡도를 노려야 하는지 역산**할 수 있다.
(대략 1초에 1억 연산 기준)

| n 범위 | 허용 복잡도 | 떠올릴 것 |
|---|---|---|
| n ≤ 10 | `O(n!)`, `O(2ⁿ)` | 완전탐색, 순열, 백트래킹 |
| n ≤ 20 | `O(2ⁿ)` | 비트마스크, 부분집합 |
| n ≤ 500 | `O(n³)` | 3중 반복, 플로이드-워셜 |
| n ≤ 5,000 | `O(n²)` | 2중 반복, DP |
| n ≤ 100,000 | `O(n log n)` | 정렬, 힙, 이진탐색 |
| n ≤ 1,000,000 | `O(n)` | 해시맵, 투 포인터, 슬라이딩 윈도우 |
| n ≥ 10,000,000 | `O(log n)`, `O(1)` | 수학적 접근, 이진탐색 |

**문제를 읽으면 Constraints부터 본다.** n = 100,000이면 "2중 반복문은 안 되겠구나"가 바로 나와야 한다.
이건 코딩테스트에서 가장 실전적인 스킬이다.

## 입력이 "숫자 값"일 때 — `log n` 의 등장

지금까지는 `n` 이 **배열 길이·문자열 길이**였다. 입력이 **숫자 하나**면 얘기가 달라진다.

```
n = 2,147,483,647        ← 값은 21억
자릿수 = 10개            ← 실제로 훑는 건 10번
```

**`O(n)` 이면 21억 번**이라는 뜻이다. 실제로는 몇십 번이면 끝난다.

```
n = 9        자릿수 1
n = 99       자릿수 2      ← 값은 11배인데 자릿수는 +1
n = 999      자릿수 3

자릿수 ≈ log₁₀(n) + 1
```

> ### 🔑 **"값이 곱셈으로 커질 때 작업량이 덧셈으로 커진다" — 이게 `log` 다.**

| 입력이 무엇인가 | 흔한 복잡도 |
|---|---|
| 배열/문자열 **길이** `n` | `O(n)`, `O(n log n)`, `O(n²)` |
| **숫자 값** `n` — 자릿수를 훑음 | **`O(log n)`** ([0202. Happy Number](../02-Hashmap/0202-happy-number/README.md)) |
| **숫자 값** `n` — 값만큼 반복 | `O(n)` (에라토스테네스 체 등) |
| 정렬된 배열에서 절반씩 버림 | **`O(log n)`** (이진 탐색) |

**판별**: *"입력이 10배 커지면 작업이 10배 늘어나나, 아니면 한 단계만 늘어나나?"*
한 단계만 늘어나면 `log`.
