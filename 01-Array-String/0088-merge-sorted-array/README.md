# 88. Merge Sorted Array

- **난이도**: Easy
- **유형**: 배열, 투 포인터
- **링크**: https://leetcode.com/problems/merge-sorted-array/
- **최초 풀이**: 2026-08-02 / **결과**: 통과 (첫 시도)

---

## 문제 요약

정렬된 배열 `nums1`(유효 원소 `m`개, 뒤에 0으로 패딩되어 총 길이 `m+n`)과 `nums2`(길이 `n`)가 주어진다.
두 배열을 병합해 **`nums1`을 in-place로 수정**하라. 반환값 없음.

---

## 접근 사고 흐름

**신호 1 — "길이가 왜 m이 아니라 m+n이지?"**
→ 뒤쪽 `n`칸은 쓰레기값(0)이자, 답을 담을 **빈 공간**이다. 출제자가 공간을 미리 준 것.

**신호 2 — "두 배열 다 이미 정렬돼 있다"**
→ 정렬된 배열이 둘 → **투 포인터**를 의심한다. 다시 sort 하는 건 이미 있는 정보를 버리는 것.

**신호 3 — "in-place로 수정하라"**
→ `nums1 = [...]` 같은 **재할당은 절대 안 된다.** 파라미터 재할당은 호출자의 배열을 바꾸지 못한다.
→ `splice` / `push` / `sort` / 인덱스 대입 같은 **변형(mutating) 연산**만 유효하다.

---

## 내 풀이 (통과)

```ts
function merge(nums1: number[], m: number, nums2: number[], n: number): void {
  nums1.splice(m)
  nums2.splice(n)
  nums1.push(...nums2)
  nums1.sort((a, b) => a - b)
}
```

- 시간 `O((m+n) log(m+n))` / 공간 `O(m+n)` (V8 TimSort 보조 배열)

### 피드백

| # | 내용 |
|---|---|
| ✅ | `sort((a,b)=>a-b)` 비교 함수를 넣었다. **JS 최대 함정 회피** |
| ✅ | 재할당이 아닌 변형 메서드만 써서 in-place 조건을 지켰다 |
| ⚠️ | `nums2.splice(n)` 은 불필요 — 제약상 `nums2.length === n`. 게다가 **입력 인자를 훼손**하는 부작용 |
| ⚠️ | 정렬돼 있다는 정보를 버리고 다시 정렬 → `O(n log n)`. 최적은 `O(m+n)` |
| ⚠️ | `push(...nums2)` 스프레드는 대형 배열에서 스택 오버플로 위험 |

## 최적 풀이 — 뒤에서부터 투 포인터

### 핵심 아이디어

**앞에서 병합하면 안 되는 이유**: `nums1[0]`에 값을 쓰는 순간, 아직 비교하지 않은 원래 `nums1[0]`이 덮어써진다.

**뒤에서 병합하면 되는 이유**: 쓰기 위치는 항상 `m+n-1`부터 줄어드는데, 이 자리는 언제나
(a) 패딩 영역이거나 (b) 이미 읽고 소비한 자리다. **덮어쓸 위험이 원천적으로 없다.**

> 빈 공간이 **뒤에** 있으니 **뒤에서부터** 채운다.

```js
function merge(nums1, m, nums2, n) {
  let i = m - 1;       // nums1의 마지막 유효 원소
  let j = n - 1;       // nums2의 마지막 원소
  let k = m + n - 1;   // 쓸 위치 = 배열의 진짜 끝

  while (j >= 0) {
    if (i >= 0 && nums1[i] > nums2[j]) {
      nums1[k--] = nums1[i--];
    } else {
      nums1[k--] = nums2[j--];
    }
  }
}
```

- 시간 `O(m+n)` / 공간 `O(1)`

### 왜 `while (j >= 0)` 인가

`i`가 먼저 소진되면(`i < 0`) 남은 `nums2`를 계속 옮겨야 하므로 루프를 돌아야 한다.
반대로 **`j`가 먼저 소진되면 남은 `nums1` 원소는 이미 제자리에 있다** — 옮길 필요가 없다.
그래서 종료 조건은 `j`만 보면 충분하다. (`i >= 0 && ...` 가드는 이 때문에 필요하다.)

## 재풀이 기록 — 2026-08-02 (같은 날, 투 포인터로 재도전)

힌트만 받고 스스로 최적해 도달. **첫 시도에 구조 버그 2개 → 수정 후 정답.**

### 1차 시도에서 낸 버그

```ts
for (let j = n-1; j >= 0; j--) {
  if (nums1[i] > nums2[j]) { nums1[k] = nums1[i]; i--; k--; }
  else                     { nums1[k] = nums2[j]; i--; k--; }  // ❌ i-- 
}
```

두 버그는 사실 **같은 뿌리**였다:
1. `else`에서 `i--` → `nums2`에서 가져왔는데 `nums1` 포인터를 움직임 → `nums1[i]`가 비교도 못 하고 증발
2. `for`문이 매번 `j--` → `if` 분기에서도 `j`가 줄어듦

결과: 매 반복마다 `i`, `j`가 **둘 다** 감소 → `[1,2,3,0,0,0] + [2,5,6]` = `[1,2,3,2,5,6]` (오답)

### 원칙 (반드시 기억)

> **값을 가져온 쪽의 포인터만 움직인다. `k`는 한 칸 채웠으니 항상 움직인다.**

| 가져온 곳 | 움직일 포인터 |
|---|---|
| `nums1` (if) | `i`, `k` |
| `nums2` (else) | `j`, `k` |

→ 이 구조는 `for`로 표현 불가. `j`를 **조건에만** 쓰고 감소는 분기 안에서 → `while`

### 최종 정답

```ts
function merge(nums1: number[], m: number, nums2: number[], n: number): void {
  let i = m - 1;
  let j = n - 1;
  let k = m + n - 1;

  while (j >= 0) {
    if (i >= 0 && nums1[i] > nums2[j]) {
      nums1[k--] = nums1[i--];
    } else {
      nums1[k--] = nums2[j--];
    }
  }
}
```

---

## ⚠️ `i >= 0` 가드 — "우연히 맞는 코드"의 위험

가드를 빼도 **LeetCode는 통과한다.** 이유:

```js
nums1[-1]        // undefined
undefined > 3    // false  (NaN 비교는 항상 false)
undefined < 3    // false
```

`i < 0`이면 비교가 항상 `false` → 항상 `else` → `nums2`에서 가져옴 → **의도한 동작과 일치.**

### 그런데 왜 고쳐야 하나

**논리적으로 동등한 코드로 바꾸면 깨진다:**

```ts
if (nums2[j] >= nums1[i]) { nums1[k--] = nums2[j--] }
else                      { nums1[k--] = nums1[i--] }   // ← i=-1이면 여기로
```
`nums2[j] >= undefined` → `false` → `else` → `nums1[k] = undefined` **폭발**

| 이유 | 설명 |
|---|---|
| 취약함 | 비교 방향만 뒤집어도 깨진다 |
| 언어 의존 | Java `ArrayIndexOutOfBoundsException`, C++ UB. JS만 관대 |
| 면접 감점 | "i가 음수면요?" → "돌려보니 되던데요"는 실패 |
| TS가 거짓말 | `nums1[i]` 타입은 `number`지만 런타임은 `undefined`. `noUncheckedIndexedAccess` 켜면 `number \| undefined`로 잡힌다 |

> **교훈: "통과했다"와 "왜 되는지 안다"는 다르다.**

## 알아야 할 상식

### 1. `sort()`의 기본 동작 — JS 최대 함정

```js
[1, 10, 2, 30].sort()            // [1, 10, 2, 30]  ← 문자열 비교!
[1, 10, 2, 30].sort((a,b)=>a-b)  // [1, 2, 10, 30]  ← 올바름
```
비교 함수를 생략하면 원소를 **문자열로 변환해 사전순** 정렬한다. 숫자 정렬엔 항상 `(a,b)=>a-b`.

### 2. 재할당 ≠ in-place

```js
function f(arr) { arr = [9, 9]; }        // ❌ 호출자에 반영 안 됨
function g(arr) { arr[0] = 9; }          // ✅ 반영됨
function h(arr) { arr.splice(0, arr.length, 9, 9); }  // ✅ 반영됨
```
파라미터는 **참조의 복사본**이다. 참조를 갈아끼우는 건 로컬 변수만 바꾼다.

### 3. `splice` vs `slice`

| 메서드 | 원본 변경 | 반환 |
|---|---|---|
| `slice(s, e)` | ❌ 안 함 | 잘라낸 **복사본** |
| `splice(s, cnt, ...items)` | ✅ 함 | **삭제된** 원소들 |

이름이 비슷해서 실수하기 쉽다. **spl**ice = **mutates**로 외우면 편하다.

#### ⚠️ `splice`는 새 배열을 할당한다

```js
const arr = [1, 2, 3, 0, 0, 0];
arr.splice(3);   // 반환값 [0,0,0] 배열이 생성됨 — 안 받아도 만들어진다
```

반환값을 버려도 **그 순간 n칸을 점유**한다. 공간복잡도는 **실행 중 최대 추가 메모리(peak)** 를 세므로, 즉시 GC되더라도 `O(n)`으로 카운트한다.

**`O(1)`로 자르려면**:
```js
arr.length = m;   // ✅ 제자리 자르기, 할당 없음
arr.length = 0;   // 배열 비우기 관용구
```

**핵심 구분**: `pop`/`shift`는 **원소 하나**를 반환 → 할당 없음. `splice`는 **배열**을 반환 → 할당 발생.

| 메서드 | 새 배열 생성 |
|---|---|
| `splice` / `slice` / `concat` / `map` / `filter` | ✅ |
| `push` / `pop` / `shift` / `unshift` / `forEach` | ❌ |
| `arr.length = k` | ❌ |
| `sort` / `reverse` | 원본 변형 (단 `sort`는 내부 버퍼 `O(n)`) |

### 4. 배열 메서드 시간복잡도

| 메서드 | 복잡도 | 비고 |
|---|---|---|
| `push` / `pop` | `O(1)` | 끝 조작은 저렴 |
| `shift` / `unshift` | `O(n)` | **앞 조작은 전체 재배치** — BFS 큐로 쓰면 병목 |
| `splice` | `O(n)` | |
| `indexOf` / `includes` | `O(n)` | 반복 조회면 `Set`으로 |
| `sort` | `O(n log n)` | |

### 5. 스프레드 인자 개수 한계

```js
arr.push(...big)   // big이 십수만 개면 RangeError: Maximum call stack size exceeded
```
스프레드는 각 원소를 **개별 인자**로 펼치므로 엔진의 인자 개수 상한에 걸린다.
대량 병합은 루프나 `for (const x of big) arr.push(x)` 로.
