# 26. Remove Duplicates from Sorted Array

- **난이도**: Easy
- **유형**: 배열, 투 포인터 (읽기-쓰기 포인터)
- **링크**: https://leetcode.com/problems/remove-duplicates-from-sorted-array/
- **최초 풀이**: 2026-08-02 / **결과**: 1차 오답 → 수정 후 통과

---

## 문제 요약

**정렬된** 배열에서 중복을 제거해 각 값이 한 번씩만 남게 하고, 남은 개수 `k`를 반환.
- 앞쪽 `k`칸만 채점
- **순서(정렬 상태) 유지 필수** ← [0027. Remove Element](../0027-remove-element/README.md) 와 다른 점

---

## 접근 사고 흐름

[0027. Remove Element](../0027-remove-element/README.md) 와 **완전히 같은 템플릿**. 조건문만 바뀐다.

```js
let k = 0;
for (...) {
  if ( 살릴_조건 ) nums[k++] = num;
}
return k;
```

**"살릴 조건"을 정하려면 무엇과 비교해야 하나?**
→ **직전에 살리기로 확정한 값** = `nums[k-1]`

---

## 1차 시도 — 오답

```ts
let k = 1
for (let i = 0; i < nums.length; i++) {
  if (nums[k] !== nums[i] && nums[k-1] !== nums[i]) {   // ❌ 앞 조건이 문제
    nums[k++] = nums[i]
  }
}
```

### 반례: `nums = [1, 2]` → `1` 반환 (정답 `2`)

| i | k | `nums[k] !== nums[i]` | `nums[k-1] !== nums[i]` | 결과 |
|---|---|---|---|---|
| 0 | 1 | `nums[1]=2 !== 1` ✅ | `nums[0]=1 !== 1` ❌ | 스킵 |
| 1 | 1 | `nums[1]=2 !== nums[1]=2` ❌ | — | 스킵 |

### 원인

`i === k` 인 순간 `nums[k] !== nums[i]` 는 **자기 자신과의 비교** → 항상 `false` → 살릴 값도 버림.
`i === k` 는 "여태 중복이 없어서 쓰기가 읽기를 따라잡은 상태". 중복 없는 배열에서 계속 발생.

### 더 근본적으로

```
nums = [1, 2, 2, 3]
        ↑  ↑
      확정  아직 미확정 (원본 쓰레기값)
      k-1   k
```

`nums[k]`는 **다음에 쓸 빈칸**이다. 거기 든 값은 아직 처리 안 된 원본일 뿐 **아무 의미가 없다.**

> **비교 대상은 오직 `nums[k-1]` — 내가 이미 살리기로 확정한 마지막 값.**

---

## 최종 정답

```ts
function removeDuplicates(nums: number[]): number {
  let k = 1                                  // nums[0]은 무조건 살아남음 → 확정 처리
  for (let i = 1; i < nums.length; i++) {    // 읽기도 1부터 (k와 앞뒤 맞춤)
    if (nums[k-1] !== nums[i]) {
      nums[k++] = nums[i]
    }
  }
  return k
}
```

- 시간 `O(n)` / 공간 `O(1)`
- 제약조건 `1 <= nums.length` 이므로 `k = 1` 시작 안전

---

## 핵심 — "정렬되어 있다"가 공간복잡도를 결정한다

```
정렬됨 → 같은 값은 반드시 붙어 있다
[0,0,1,1,1,2,2,3,3,4]
 └┘ └───┘ └─┘ └─┘
```

같은 값이 뭉쳐 있으니 **직전 확정값 하나만 기억**하면 충분 → `O(1)`

만약 정렬이 안 돼 있다면? `[1,3,1]` 때문에 **지금까지 나온 모든 값**을 기억해야 함 → `Set` 필요 → `O(n)`

> **"정렬되어 있다"는 조건이 공간을 `O(n)` → `O(1)`로 만든다.**
> 문제에서 "sorted"를 보면 반드시 멈춰서 이 이득을 챙길 수 있는지 생각할 것.

## 알아야 할 상식

### 1. ⚠️ LeetCode의 `runtime` 수치는 신뢰하지 말 것

같은 코드를 두 번 제출하면 `0ms` / `3ms` 가 왔다갔다 한다. 이유:

| 원인 | 설명 |
|---|---|
| 측정 해상도 | ms 단위. `n ≤ 3×10⁴` 의 `O(n)` 은 실제 **수십~수백 마이크로초** → ms로 반올림하면 대부분 `0` |
| 서버 부하 | 채점 서버가 그 순간 얼마나 바쁜지에 좌우 |
| JIT 워밍업 | V8이 최적화 컴파일을 언제 트리거하는지 실행마다 다름 |
| 테스트케이스 순서 | 캐시 상태 영향 |

> **판단 기준은 항상 복잡도(Big-O)지 `runtime` 숫자가 아니다.**
> `0ms`를 쫓아 코드를 꼬는 건 시간 낭비다. 면접관도 `runtime`을 안 본다.

### 2. 자기 자신에게 쓰기(self-write)

내 코드는 중복이 없으면 `k === i` 라서 `nums[i] = nums[i]` 자기 대입이 발생한다.

```js
[1,2,3,4,5]  →  4번의 self-write (값은 그대로)
```

[0027. Remove Element](../0027-remove-element/README.md) 에서 다룬 **"쓰기 횟수"** 논의와 같은 맥락.
피하려면 `if (k !== i) nums[k] = nums[i]; k++;` 로 분기를 추가할 수 있지만,
**분기 예측 실패 비용 > 캐시에 있는 메모리 쓰기 비용** 이라 오히려 손해일 수 있다. **하지 말 것.**

### 3. `nums[k-1]` 대신 `nums[i-1]` 로 비교해도 된다

```ts
if (nums[i] !== nums[i-1]) nums[k++] = nums[i]   // 이것도 정답
```

**왜 되나?** 불변식 `k ≤ i` 때문에 위치 `i-1` 은 **항상 원본값을 유지**한다.
- `k < i` 면 → 쓰기는 `0..k-1` 에만 발생, `i-1 ≥ k` 이므로 안 건드림
- `k === i` 면 → 그 자리는 self-write 였으므로 값이 그대로

둘 다 맞지만 **`nums[k-1]` 쪽이 의미가 더 명확**하다 ("마지막으로 확정한 값").
80번(중복 2개까지 허용)으로 확장할 때도 `nums[k-2]` 로 자연스럽게 이어진다.

### 4. 템플릿 확장

| 문제 | 조건 |
|---|---|
| 27. Remove Element | `nums[i] !== val` |
| **26. (이 문제)** | `nums[i] !== nums[k-1]` |
| 80. Remove Duplicates II | `k < 2 \|\| nums[i] !== nums[k-2]` |
| 283. Move Zeroes | `nums[i] !== 0` (+ 뒤를 0으로) |

## 실수 노트

- **아직 안 쓴 자리(`nums[k]`)와 비교했다** → 쓰기 포인터가 가리키는 곳은 "다음에 쓸 빈칸". 의미 있는 값은 `nums[k-1]`
- `k = 1`로 시작해놓고 `i = 0`부터 읽었다 → **시작점을 바꿨으면 짝이 되는 쪽도 같이 확인**
- ✅ 복잡도 명시함 (3번째 문제 만에 습관화)

### +7일 복습 기록 — 2026-08-12

백지 재작성 **통과**. node 고정 10건 + 랜덤 20만건 불일치 0. 복잡도 `O(n)` / `O(1)` 정확.

```ts
function removeDuplicates(nums: number[]): number {
    let i = 1
    let k = 1

    for (i; i < nums.length; i++) {
        if (nums[k-1] !== nums[i]) {
            nums[k++] = nums[i]
        }
    }

    return k
}
```

**"왜 되는가"도 스스로 설명함**: 정렬되어 있으므로 같은 값은 붙어 있고, 한 번 지나친 값은 뒤에서 다시 나올 수 없다 → 직전 확정값 하나만 기억하면 충분.

#### ⚠️ 같은 실수 재발 — `nums[k]` 와 비교

08-02 실수 노트의 첫 줄이 **그대로 재발**했다. 코드가 아니라 **접근 단계**에서.

| 08-02 (1차 오답) | 08-12 (복습 접근 1차) |
|---|---|
| `nums[k] !== nums[i] && nums[k-1] !== nums[i]` | `nums[k-1] !== nums[k] && nums[k] !== nums[i]` |

형태는 달라도 뿌리는 같다 — **아직 안 쓴 자리 `nums[k]` 를 비교에 넣었다.**
`nums = [1,1,2]` 로 트레이스하자 `k=1`, `[1]` 반환(정답 `k=2`, `[1,2]`)이 드러나면서 스스로 `nums[k-1] !== nums[i]` 하나로 정리. → `#쓰기포인터오해` 3회

> 🔑 **`nums[k]` = 다음에 쓸 빈칸. 의미 있는 값은 `nums[k-1]`.**
> 매번 이걸 물어라 — **"내가 지금 비교하는 칸은 이미 확정된 값인가, 아직 안 쓴 자리인가?"**

**미재발 ✅**: `k = 1` 시작인데 `i = 0` 부터 읽던 실수 — 이번엔 둘 다 `1`로 정확히 시작

**접근 먼저 받는 방식이 실제로 버그를 막았다.** 구현 단계에서는 한 번도 안 틀렸다.

**스타일**: `let i = 1` 을 루프 밖에서 선언하고 `for (i; ...)` 로 초기화 자리를 비워둠 → `for (let i = 1; ...)` 로. 변수 수명은 필요한 만큼만. (카운트 미포함)
